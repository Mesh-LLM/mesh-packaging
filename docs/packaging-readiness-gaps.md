# Packaging readiness gaps

Audit date: 2026-06-16

## Upstream sync findings (readiness prerequisite)

Target repository inspected: `Mesh-LLM/mesh-llm`

Upstream snapshot inspected:
`8f5dacfc46a3cfa8a769679cdb982bb7f40adef6` on `main`

Upstream workspace version at that snapshot: `0.68.0`

The upstream sync work in this section is a prerequisite for the readiness work
below. The existing packaging scaffold is useful, but the current package and
image pipeline must first be realigned with how `mesh-llm` is now built,
published, and loaded at runtime.

### Summary

`mesh-agent-images` is internally coherent, but it is not in sync with the
current `mesh-llm` release structure.

The largest drift is the build and runtime contract. This repository still
models every Linux row as:

```text
UI dist -> static llama ABI artifact -> raw cargo build -> native package -> image
```

Current `mesh-llm` has moved to a more complex release contract:

```text
release-profile UI -> release binary/archive -> native runtime artifacts
                              -> native-runtimes.json -> runtime install/cache
```

The upstream source repo also now owns release attestation, Swift SDK artifacts,
SDK console packaging, crates.io publication, Windows bundles, Linux ARM64 CUDA,
CUDA 12.9.2/13.1.2 release lanes, ROCm 7.0 release lane, and native runtime
resolver/install commands. This repository should either consume those upstream
release assets or call the upstream release scripts directly. It should not keep
reimplementing the old build internals in Dockerfile stages.

Recommended direction: make `mesh-agent-images` a downstream packaging and
image repo. For normal releases, consume the published `mesh-llm` release
archive for the application package-manager outputs. Keep `native-runtimes.json`
and native runtime archives in the upstream `mesh-llm` release, where the
runtime install engine already owns resolution, cache, checksum, and update
policy. Keep source-build dry-run paths only when they delegate to upstream
release scripts or use the same build profile, feature flags, asset names,
checksums, and attestation behavior.

### Current upstream contract

The current upstream repository is no longer a small CLI plus patched static
llama build. Its workspace contains the CLI, command layer, config, runtime
install and native runtime crates, hardware profiling, TUI, UI, SDK/API crates,
Skippy crates, model crates, FFI/node bindings, test harnesses, and `xtask`
release tooling.

Important upstream release details observed at the inspected snapshot:

- `scripts/build-release.sh` defaults `MESH_LLM_DYNAMIC_NATIVE_RUNTIME=1`.
- Release-profile UI builds go through `scripts/build-ui.sh`, not raw
  `pnpm install && pnpm run build`.
- `scripts/build-ui.sh` stamps `.mesh-llm-ui-build-env`, forces
  `VITE_MESH_LLM_DEBUG_UI=false` for release, and sets
  `ONNXRUNTIME_NODE_INSTALL_CUDA=skip` before install.
- Native runtime artifacts are packaged by `scripts/package-native-runtime.sh`
  from dynamic llama builds using `LLAMA_STAGE_LINK_MODE=dynamic`.
- Native runtime archives are verified by
  `scripts/verify-native-runtime-package.sh`.
- `native-runtimes.json` is generated by
  `scripts/generate-native-runtime-release-manifest.sh`.
- `mesh-llm runtime install`, `runtime list`, `runtime prune`, and
  `--bundle-dir` are now part of the distribution contract.
- `install.sh` installs the release archive, then attempts to install the
  recommended native runtime from the release manifest.
- Release archives are built with upstream `just release-build*` and
  `just release-bundle*` recipes, which flow through `scripts/package-release.sh`
  or `scripts/package-release.ps1`.
- `scripts/package-release.sh` can stamp and inspect embedded release
  attestation when signing keys are present.
- Upstream release lanes currently include macOS aarch64 Metal, Linux x86_64
  CPU, Linux ARM64 CPU, Linux ARM64 CUDA, Linux CUDA, Linux CUDA Blackwell,
  Linux ROCm, Linux Vulkan, Windows CPU, Windows CUDA, Windows ROCm, Windows
  Vulkan, SwiftPM XCFramework, and crates.io SDK crate publication.
- Upstream Linux CUDA lanes use CUDA `12.9.2` and `13.1.2`.
- Upstream Linux ROCm release uses `rocm/dev-ubuntu-24.04:7.0-complete`.
- Upstream Linux Vulkan is a release lane, not only an experimental matrix row.

There is one upstream ambiguity to track: the `justfile` comment says GitHub
release builds use embedded ABI libraries, but `scripts/build-release.sh`
currently defaults to dynamic native runtimes. GPU release recipes still call
`scripts/build-linux.sh`, which builds embedded/static llama artifacts. Treat the
actual scripts and release workflow as source of truth, and confirm upstream
intent before changing this repository's binary/runtime split.

### Gap analysis by packaging area

#### Cross-cutting release contract

Current gap: this repo builds its own release-like binaries instead of using the
current upstream release contract.

Required sync work:

- Use upstream release archives and runtime assets as the default packaging
  input when packaging an official `mesh-llm` release.
- For dry-runs or pre-release source builds, delegate to upstream
  `just release-build*` and `just release-bundle*` recipes, or to the underlying
  upstream scripts with the same environment.
- Stop treating the static llama ABI directory as the universal correctness
  artifact. It is only correct for embedded/static lanes.
- Track the upstream hybrid explicitly: some release lanes are dynamic runtime
  aware, while GPU release lanes may still be embedded/static at the inspected
  snapshot.
- Preserve upstream asset names, version stamping, checksums, and release
  attestation status.

#### Docker and runtime images

Current gap: Docker images still install a package containing a locally built
`mesh-llm` binary, and the source-build path was not yet aligned with the
dynamic runtime feature used by upstream release builds.

Required sync work:

- Replace the direct UI build in `docker/Dockerfile.mesh-llm` with upstream
  `scripts/build-ui.sh` for source-build paths.
- Build source artifacts with `MESH_LLM_BUILD_PROFILE=release`.
- Set or derive `MESH_LLM_BUILD_VERSION` the same way upstream release scripts
  do.
- Use `cargo build --release --locked` when a direct cargo build remains.
- Build source artifacts with `MESH_LLM_DYNAMIC_NATIVE_RUNTIME=1` by default so the app
  binary matches upstream runtime-engine expectations.
- Keep native runtime archives, `native-runtimes.json`, and runtime cache
  contents out of image/package artifacts. Those assets remain upstream
  `mesh-llm` release assets consumed by `mesh-llm runtime install`.
- Add image QA that verifies `mesh-llm --version`, the runtime command
  help/list surface where the binary can start on the runner, and a lightweight
  `serve --headless` startup path.

#### Native Linux packages

Current gap: `.deb`, `.apk`, and `.pkg.tar.zst` packages contain only
`/usr/local/bin/mesh-llm` plus minimal package metadata.

Required sync work:

- Package the upstream release archive output, not a raw Dockerfile cargo
  binary.
- Keep native runtime assets and `native-runtimes.json` out of native package
  artifacts; package-manager outputs should install the application and let
  upstream `mesh-llm` own runtime installation/update policy.
- Add package QA that installs the package and verifies `mesh-llm --version` and
  the runtime command surface where the binary can start on the target runner,
  not only expected filenames.
- Review package dependencies against upstream runtime behavior. Current Ubuntu
  packages only add `libvulkan1` for Vulkan and do not model CUDA/ROCm runtime
  package requirements.
- Keep package names carrying version, distro, architecture, backend, and
  backend version, but update backend naming to match upstream release asset
  semantics such as `cuda-12`, `cuda-13`, and `cuda-blackwell` where applicable.

#### Matrix and runner coverage

Current gap: the local image matrix does not match upstream release lanes.

Required sync work:

- Replace Ubuntu CUDA 12.6/12.8/13.2 release rows with upstream CUDA 12.9.2 and
  13.1.2 lanes, unless older CUDA rows are deliberately kept as downstream
  support-extension rows.
- Add Linux ARM64 CUDA if this repo is expected to mirror upstream Linux release
  coverage.
- Treat ROCm 7.1 and 7.2 rows as downstream extensions until upstream release
  lanes publish those versions.
- Revalidate and promote Linux Vulkan if it is green against current upstream,
  because upstream now publishes a Linux Vulkan release bundle.
- Split rows into `upstream_mirrored` and `downstream_extension` categories so
  docs, tags, support levels, and release fan-out do not imply unsupported
  upstream guarantees.
- Decide whether Windows package/archive handling is in scope. Upstream release
  has Windows CPU/CUDA/ROCm/Vulkan bundles; this repo currently has no Windows
  packaging path.

#### Homebrew and macOS

Current gap: Homebrew staging builds and packages macOS binaries inside this
repo, with both arm64 and amd64 lanes, while upstream release currently centers
macOS distribution on aarch64 Metal release archives and SwiftPM artifacts.

Required sync work:

- Prefer consuming upstream `mesh-llm-aarch64-apple-darwin.tar.gz` for the
  Homebrew formula.
- If source-building Homebrew assets remains necessary, call upstream macOS
  release scripts and preserve release attestation behavior.
- Reconfirm whether macOS amd64 is supported. Current upstream release workflow
  publishes macOS aarch64, not macOS amd64.
- Document macOS GPU/runtime limits separately from Linux container support.
- Add Homebrew install smoke that exercises `mesh-llm runtime list` and
  `mesh-llm --version`, not only formula audit/install.

#### Cargo, SDKs, and language packages

Current gap: this repo has no real Cargo/crates.io publication path, while
upstream now publishes a defined SDK crate chain and SwiftPM binary artifact.

Required sync work:

- Decide the ownership boundary. Recommended: crates.io, SwiftPM, Node/Kotlin
  SDK resources, and SDK console asset publication remain upstream-owned.
- Document that this repo packages release binaries/images and consumes upstream
  SDK/Cargo releases; it should not duplicate `scripts/publish-crates.sh`.
- If Cargo binary installers such as `cargo binstall` are desired, create that
  as a separate packaging area with explicit metadata and QA. Do not conflate it
  with upstream crates.io SDK publication.

#### Publication, provenance, and signing

Current gap: this repo publishes package/image assets with checksums and SBOM
scaffolding, but it does not preserve upstream release attestation semantics for
the packaged executable.

Required sync work:

- Package the binary after upstream `scripts/package-release.sh` has stamped it,
  when official release signing keys are available.
- Include or document the release attestation public key expected by consumers.
- Add QA for `xtask release-attestation inspect` when packaging from source.
- Keep native package checksums, image SBOM/provenance, and release asset
  checksums, but link them to the upstream source SHA and attestation status.
- Decide package repository signing separately for `.deb`, `.apk`, Arch package
  repos, and Homebrew tap updates.

#### Workflows and reuse artifacts

Current gap: `.github/workflows/images-release.yml` still has `abi`, `binary`,
`native-package`, and `runtime-image` phases. The binary phase used restored
static ABI artifacts by default rather than upstream release archives or the
dynamic runtime feature.

Required sync work:

- Add an `upstream-release-assets` phase for official release packaging.
- Update artifact reuse validation so runtime images depend on binary packages
  only; native runtime archives/manifests remain upstream `mesh-llm` release
  assets.
- Change release dispatch from `mesh-llm` so this workflow starts only after
  upstream release assets needed by packaging are available.
- Keep `abi` phase only for embedded/static rows. Rename it if the artifact is
  no longer always an ABI input.

#### Documentation

Current gap: README, matrix docs, native package docs, and release checklist
describe the old split artifact model.

Required sync work:

- Rewrite the architecture docs around upstream release archives and the
  upstream-owned native runtime install engine.
- Document the hybrid dynamic/static state honestly until upstream converges.
- Document `upstream_mirrored` versus `downstream_extension` rows.
- Document which package areas are in scope for this repo and which remain
  upstream-owned.
- Update release checklists to include runtime command smoke, attestation
  inspection, package-manager destination checks, and image startup checks.

## Packaging readiness audit

This repository is partially ready. It has a coherent artifact pipeline, matrix
source of truth, Docker targets, native Linux package builders, macOS Homebrew
asset generation, release-asset promotion, and provenance scaffolding. It is not
ready to be the complete public packaging and publication home for every
intended `mesh-llm` channel until the upstream sync prerequisite above and the
readiness gaps below are closed.

The key distinction is that this repo is release-shaped, but not yet fully
release-proven across every package area. CPU Linux rows and macOS/Homebrew
scaffolding have the strongest implementation story, but those areas must be
revalidated against the current upstream release model before they can be
treated as ready. GPU, Vulkan, distro repository publication, Cargo/crates
distribution, signing, and full matrix evidence still need work.

The current numeric scorecard is tracked separately in
`docs/packaging-readiness-scorecard.md`. The release benchmark is 85/100
overall, no release-blocking aspect below 80/100, and publish-safety controls at
95/100 or higher.

- Linux packages and macOS tarballs are the current user-facing binary
  distribution outputs.

Gaps:

- This repository does not publish Rust crates to crates.io.
- There is no `cargo package` or `cargo publish` workflow for the upstream
  Rust workspace.
- There is no Cargo-based installer channel such as `cargo binstall`, archive
  metadata for cargo installers, or standalone generic Linux tarball path.
- Rust toolchain selection depends on installed stable toolchains in the build
  environment unless the upstream source checkout pins a toolchain. That is a
  build reproducibility risk for long-lived release support.

## Publication, signing, and provenance

Implemented:

- Published runs create or reuse a GitHub Release in this repository.
- Native package files, checksums, package SBOMs, image digest records, image
  SBOMs, and attestation verification notes are promoted as durable release
  assets.
- Binary/package artifact attestations and image digest attestations are wired
  into the workflow.
- Package signing policy blocks apt/apk/pacman repository publication until
  signing and key operations are ready.

Gaps:

- Native package repository signing is policy-only right now. There are no
  signing jobs, keys, key publication docs, or key-rotation dry-runs.
- apt/apk/pacman repositories do not exist.
- Most GitHub Actions are referenced by version tags rather than commit SHAs.
  Only the Anchore/Syft SBOM action is pinned by SHA.
- There is no automated verification job that consumes the final GitHub Release
  assets and proves checksums, SBOM presence, and attestation verification from
  a clean environment.

## CI, runners, and local developer validation

Implemented:

- Precheck validates matrix generation, representative matrices, image matrix
  tests, Homebrew helper tests, native package QA placeholders, and Dockerfile
  `--check` targets.
- Release workflow supports GitHub-hosted Linux/macOS runners by default and
  Carrack self-hosted AMD64 mode for trusted manual release-tag probes.
- Runner guidance and GPU failure runbooks are documented.

Gaps:

- Precheck is mostly static and placeholder-based. It is valuable, but it does
  not prove package/image runtime behavior for all rows.
- Local Docker availability is a prerequisite for package install QA and
  Dockerfile checks, and this audit could not run those Docker checks.
- ShellCheck is not clean without addressing intentional SC2016 warnings.
- Full GPU validation depends on real CUDA/ROCm/Vulkan runner capability, not
  on the matrix generator or Dockerfile checks.

## Bottom line

This repo is a strong packaging control plane, but it should not yet be treated
as fully ready for all `mesh-llm` Docker, Homebrew, Cargo, and native package
publication. The next useful release-readiness slice is to prove the default
Linux matrix through the full package-first image chain, add final image smoke
tests, and decide the Cargo/tap/repository signing scope before expanding the
public distribution surface.
